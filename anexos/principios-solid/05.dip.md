# Principio de Inversión de Dependencias (DIP)

## Propósito y Tipo del Principio SOLID

El Principio de Inversión de Dependencias (DIP) es un principio de diseño estructural y arquitectónico. Su propósito establece que los módulos de alto nivel (la lógica de negocio central) no deben depender de los módulos de bajo nivel (detalles de infraestructura, bases de datos o UI). Ambos deben depender de abstracciones (interfaces o clases abstractas). Además, las abstracciones no deben depender de los detalles, sino que los detalles deben depender de las abstracciones.

## Motivación

En el boceto inicial del sistema, se detectaron dos problemas principales de acoplamiento que violan este principio:

1. **Acoplamiento de Dominio:** La clase `Item_pedido` dependía directamente de la clase concreta `Producto`, dejando a la clase `Combo` aislada. Esto contradice el Requisito Funcional RF1, que permite incluir tanto productos individuales como combos dentro de un mismo pedido.
2. **Acoplamiento de Infraestructura:** El sistema requiere guardar los pedidos y enviarlos automáticamente a la cocina (RF2). Si los servicios del sistema instancian directamente conexiones a bases de datos específicas o envían datos a pantallas físicas concretas, el software se vuelve rígido, frágil e imposible de probar mediante pruebas unitarias aislando la infraestructura.

## Explicación de Clases Abstractas e Interfaces

En el Diseño Orientado a Objetos (DOO), las abstracciones son las herramientas principales para desacoplar componentes:

* **Clase Abstracta:** Es una clase que no se puede instanciar directamente y que sirve como plantilla base para una jerarquía de clases. Puede contener tanto firmas de métodos como implementaciones de código o atributos compartidos por sus subclases.
* **Interfaz:** Es un contrato puro que define un conjunto de operaciones que una clase concreta debe implementar, sin proveer ningún tipo de código fuente ni estado interno.

Para cumplir con DIP, se invierten las dependencias introduciendo interfaces en los límites del sistema. En lugar de que la lógica de negocio llame a una tecnología externa concreta, la lógica define una interfaz (puerto). Las herramientas tecnológicas externas actúan como complementos o *plugins* que se adaptan a ese contrato, garantizando que el flujo de control y las dependencias apunten hacia las políticas de alto nivel.

## Justificación Técnica

El diagrama muestra la resolución de las dependencias a través de inyección e interfaces:

* **Abstracción en el Catálogo (`ElementoMenu`):** Se creó la interfaz `ElementoMenu`. Tanto `Producto` como `Combo` implementan esta abstracción. Ahora, `Item_pedido` depende únicamente de la interfaz `ElementoMenu` (obteniendo el nombre y precio vigente), desconectándose de las clases concretas y permitiendo futuras extensiones del catálogo.
* **Puertos de Infraestructura:** Se definieron las interfaces `RepositorioPedidos` (para la persistencia), `CatalogoMenu` (para consultar ítems) y `PublicadorComandasCocina` (para notificar a la cocina sin acoplarse a una tecnología de red o pantalla específica).
* **Inyección de Dependencias:** Los casos de uso son manejados por servicios de aplicación (como `ServicioTomarPedido`). Este servicio no crea sus propias dependencias, sino que recibe las implementaciones concretas a través de su constructor (inyección de dependencias). Esto asegura que el servicio orqueste la lógica pura (construye el pedido, lo guarda y solicita su publicación) sin conocer *cómo* se guarda o *cómo* se envía.
